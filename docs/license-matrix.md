# 许可证对比表

本表内容与 `license_picker/data/licenses.json` 保持一致，改数据时请同步更新这里。

| SPDX | 名称 | 类型 | 专利授权 | 商标授权 | OSI | 核心义务 |
|---|---|---|---|---|---|---|
| MIT | MIT 许可证 | 宽松 | 无 | 无 | 是 | 保留版权声明与许可文本 |
| Apache-2.0 | Apache 许可证 2.0 | 宽松 | 有 | 无 | 是 | 保留版权、许可与 NOTICE；标注修改；不得暗示商标授权 |
| BSD-3-Clause | BSD 三条款许可证 | 宽松 | 无 | 无 | 是 | 保留声明；不得用作者名义背书 |
| MPL-2.0 | Mozilla 公共许可证 2.0 | 弱 copyleft | 有 | 无 | 是 | 修改过的源文件需以 MPL 公开 |
| LGPL-3.0 | GNU 宽通用公共许可证 3.0 | 弱 copyleft | 有 | 无 | 是 | 修改库本体需开源；允许重新链接 |
| GPL-3.0 | GNU 通用公共许可证 3.0 | 强 copyleft | 有 | 无 | 是 | 衍生作品整体开源并附源码 |
| AGPL-3.0 | GNU Affero 通用公共许可证 3.0 | 网络 copyleft | 有 | 无 | 是 | 同 GPL，且网络提供服务也算分发 |
| CC0-1.0 | CC0 1.0 公共领域贡献 | 公共领域 | 无 | 无 | 否 | 无强制义务 |

## 宽松三兄弟怎么选

- **MIT**：只想写一行“保留声明”，项目不含专利实现，选它。
- **Apache-2.0**：公司要过法务、实现里可能有专利、需要专利反诉保护，选它。代价是文本长、要维护 `NOTICE`。
- **BSD-3-Clause**：和 MIT 几乎一样，多一条“不得用作者名义背书”。学术项目和高校软件常用。

## 弱 copyleft 的两条路线

- **LGPL-3.0**：面向“被链接的库”。改库要开源，动态链接它的专有软件可以闭源，但必须允许用户替换库版本。
- **MPL-2.0**：面向“文件级”场景。只要求被改过的**源文件**继续以 MPL 公开，其余文件可以闭源。浏览器扩展、被嵌进商业产品的组件常用。

## 强 copyleft 与 SaaS 漏洞

GPL-3.0 的分发义务只在你**分发**软件时触发。把 GPL 程序部署成网站对外提供服务，并不构成分发，所以云厂商可以在不分发源码的情况下用它赚钱——这就是常说的 **SaaS 漏洞**。AGPL-3.0 补上了这一条：只要用户通过网络与它交互，就有权拿到源码。

代价也很直接：AGPL 会劝退相当一部分商业用户，包括一些公司明令禁止引入 AGPL 依赖。个人项目、基础设施类项目用它比较常见。

## 三个常见误解

1. **“MIT 最短所以最自由”**——宽松的是义务，不是权利。MIT 不提供专利授权，专利权人仍可能单独主张专利。
2. **“用了 GPL 库我的项目就必须开源”**——取决于是否构成衍生作品、是链接还是进程间调用，法律上远比口诀复杂。工程上的稳妥做法是：拿不准就问，别赌。
3. **“CC0 可以用于代码”**——CC0 不处理专利，也不被 OSI 认定为软件许可证。数据集和文档可以用，代码基线建议还是选 OSI 认证的许可证。
